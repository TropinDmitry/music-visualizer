# Music Visualizer: ТЗ на прототип

## Зачем
Личный проект пользователя с прицелом на монетизацию. Музыкант загружает трек, выбирает стиль визуализации, реагирующей на звук, и скачивает видео (для YouTube, ВК, клипов). Возможная модель денег — разовая оплата за экспорт без водяного знака или за наборы стилей, без подписки. В прототипе оплаты нет, только переключатель водяного знака.

Визуал генерируется **не нейросетью, а процедурно**: анализ звука (громкость, полосы частот, удары) каждый кадр управляет шейдерами и сценой Three.js.

## Стек
- React + TypeScript + Vite, Three.js (свои шейдеры GLSL), Web Audio API.
- Экспорт: WebCodecs (`VideoEncoder` и `AudioEncoder`) и MP4-мультиплексор. Выбрать актуальную поддерживаемую библиотеку (кандидаты — mediabunny, mp4-muxer; проверить статус и версию). Если WebCodecs недоступен, запасной вариант — `MediaRecorder` (WebM в реальном времени).
- Бэкенда нет.

## Что сделать
1. **Загрузка трека** (mp3, wav, ogg) и `decodeAudioData`.
2. **Офлайн-анализ** заранее, по кадрам при заданном FPS.
   - Что считать: FFT, энергия в полосах (бас, середина, верх), RMS, детектор ударов (onset), сглаживание.
   - Анализ детерминированный, поэтому экспорт совпадает с превью и может идти быстрее реального времени.
3. **Превью** с проигрыванием и синхронизацией по `audioContext.currentTime`, перемотка.
4. **2–3 стиля**, например:
   - частицы или сфера, которая «дышит» басом, со вспышкой на ударах;
   - кольцевой спектр или волна;
   - шейдерный фон (туннель, плазма) с реакцией на полосы.
   - У каждого стиля 3–5 параметров: цвета или палитра, интенсивность, скорость.
5. **Опции экспорта.**
   - Разрешение: 1920×1080, 1080×1920 (вертикальное), 1080×1080.
   - 30 или 60 FPS, прогресс-бар, отмена.
   - Водяной знак (вкл./выкл.), название трека и исполнителя текстом.
6. **Экспорт MP4** со звуком: рендер кадров в offscreen canvas фиксированного размера, кодирование, мультиплексирование, скачивание файла.

## Проверка
- Unit-тесты (vitest) анализатора на синтетических сигналах:
  - синус 60 Гц попадает в бас, синус 5 кГц — в верх;
  - щелчки раз в 0,5 с находятся детектором ударов;
  - тишина даёт нули.
- Запустить в браузерной панели: загрузить сгенерированный тестовый WAV (создать скриптом, ничего не скачивать), проверить превью всех стилей, экспортировать короткий ролик и убедиться, что файл создаётся и не пустой. Сделать скриншоты.
- `npm run build` и typecheck без ошибок.

## Правила
- Общение и документация на русском. Пользователь — бывший фронтенд-разработчик (JS, React, Vue, Three.js). Объяснять просто: суть, пример, подводные камни. Проект для него и для портфолио, поэтому код должен быть понятным и аккуратным.
- Факты о браузерных API и библиотеках не утверждать по памяти: проверять или помечать 🔎. Отдельно описать поддержку WebCodecs по браузерам.
- Git: коммитить локально можно; без строк про Claude в сообщениях коммитов (так пользователь просил в своём другом репозитории). Никуда не пушить и не создавать удалённые репозитории без вопроса.
- В конце: README (что это, как запустить, как добавить новый стиль), `docs/IDEAS.md` (что дальше: монетизация, конкуренты, какие фишки могут отличить продукт) и короткое резюме для пользователя.

## Стиль кода
Код должен быть читабельным и «человеческим», чтобы по нему можно было самому учиться стеку.
- Простые и явные конструкции. Без хитрых паттернов: никаких фабрик фабрик, DI, сложных дженериков, метапрограммирования. Не нужны цепочки из reduce/compose там, где хватит обычного цикла.
- Понятные имена переменных и функций. Небольшие функции с одной задачей. Плоская структура папок.
- Комментарии на русском там, где неочевидно «зачем»: особенно анализ звука и FFT, шейдеры, кодирование видео. Очевидное не комментировать.
- Типы TS простые и явные. React — функциональные компоненты и обычные хуки, без лишних абстракций и state-менеджеров, если они не нужны.
- Если что-то уже написано сложнее — упростить. В README есть короткий «путеводитель по коду»: с какого файла начать читать.
